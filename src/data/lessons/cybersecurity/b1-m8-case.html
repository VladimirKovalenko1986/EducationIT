Кейс: кібератака на «Укрінформ»

Розглянемо реальний приклад із матеріалів CERT-UA — Урядової команди реагування на комп'ютерні надзвичайні події України.

17.01.2023 близько 12:39 у телеграм-каналі «CyberArmyofRussia_Reborn» з'явилася інформація про порушення роботи кількох елементів інформаційно-комунікаційної системи (ІКС) Українського національного інформаційного агентства «Укрінформ». Того ж дня на звернення Агентства CERT-UA розпочала дослідження кібератаки.

Станом на 27.01.2023 виявлено 5 зразків шкідливих програм і скриптів, які порушують цілісність і доступність інформації: перезаписують файли й диски нулями або випадковими даними, а потім видаляють їх.
  • CaddyWiper — Windows;
  • ZeroWipe — Windows;
  • SDelete — Windows (легітимна утиліта Microsoft, яку використали зловмисники);
  • AwfulShred — Linux;
  • BidSwipe — FreeBSD.

З'ясовано, що зловмисники невдало спробували вивести з ладу комп'ютери користувачів за допомогою програм-деструкторів CaddyWiper і ZeroWipe, а також легітимної утиліти SDelete, яку мав запустити bat-файл. Для централізованого розповсюдження шкідливих програм вони створили об'єкт групової політики (GPO), який створював відповідні заплановані завдання на комп'ютерах домену.

Є підстави вважати, що розвідку ІКС «Укрінформу» зловмисники провели не пізніше 07.12.2022. Завершальну стадію атаки розпочали 17.01.2023, але вона мала лише частковий успіх — зокрема щодо кількох систем зберігання даних.

У ході дослідження визначено елемент ІКС, через який зловмисники отримали передумови для несанкціонованого віддаленого доступу. За результатами дослідження CERT-UA вважає, що атаку здійснило угруповання UAC-0082 (Sandworm), діяльність якого асоціюється з ГУ ГШ ЗС РФ.

Варто зауважити, що згаданий телеграм-канал, окрім типових повідомлень про DDoS-атаки та дефейси, ексклюзивно висвітлює саме деструктивну активність цього угруповання.

Що показують знайдені зразки

Нижче — фрагменти з дослідження. Скриншоти в оригіналі дрібні, тому під кожним є розшифровка ключових рядків і пояснення. Натисни на скриншот, щоб збільшити його.

Це фрагменти справжніх шкідливих програм. Їх наведено лише для аналізу. Ніколи не запускай такі команди чи скрипти: вони безповоротно знищують дані. Коментарі в коді (після // та #) додано для пояснення, в оригіналі їх немає, а частину рядків пропущено (...).

1. Вайпер для Windows: знищення таблиці розділів і MBR

Програма відкриває фізичний диск \\.\PHYSICALDRIVE0 і обнуляє таблицю розділів, а потім послідовно виконує три деструктивні функції:

hDevice = CreateFileW(u_\\.\PHYSICALDRIVE0, ...);
DeviceIoControl(hDevice, IOCTL_DISK_GET_DRIVE_LAYOUT_EX, ...);  // читає таблицю розділів
// обнуляє тип та ідентифікатор розділу GPT
DeviceIoControl(hDevice, IOCTL_DISK_SET_DRIVE_LAYOUT_EX, ...);  // записує зіпсовану таблицю
...
destroy_mbr(&ctx);     // знищити головний завантажувальний запис
wipe_files(&ctx);      // перезаписати файли
delete_drives(&ctx);   // знищити диски

Що варто помітити аналітику:

  • Назви функцій SetFilePointer і WriteFile зберігаються в коді у вигляді чисел (0x46746553 — це «SetF») і завантажуються динамічно через GetProcAddress. Так шкідливе ПЗ ховає підозрілі виклики від простого сигнатурного аналізу.
  • Перевірка байта ProcessEnvironmentBlock + 2 (поле BeingDebugged) — захист від налагоджувача: якщо програму аналізують у дебагері, вона просто завершується.

2. ZeroWipe: перезапис дисків нулями

Функція main запускає 26 потоків — по одному на кожен можливий фізичний диск (PhysicalDrive0–PhysicalDrive25), чекає на їх завершення, а потім виходить із системи. Кожен потік виконує thread_proc:

wsprintfW(device_name, L"\\\\.\\PhysicalDrive%d", drive_index);
hDevice = CreateFileW(device_name, ..., OPEN_EXISTING, FILE_FLAG_WRITE_THROUGH, NULL);
DeviceIoControl(hDevice, IOCTL_DISK_GET_DRIVE_GEOMETRY, ...);   // дізнається розмір сектора
lpBuffer = LocalAlloc(LMEM_ZEROINIT, geometry.BytesPerSector << 10);  // буфер із нулів
do {
    BVar1 = WriteFile(hDevice, lpBuffer, ...);   // записує нулі, поки диск не закінчиться
} while (BVar1 != 0);

3. Bat-файл із вбудованою утилітою SDelete

Скрипт містить виконуваний файл, записаний у вигляді майже 18 000 рядків шістнадцяткових чисел. Він збирає з них .exe (легітимну утиліту SDelete), а потім запускає знищення даних:

set TEMPFILE_HEX="!RANDOM!.hex"
>%TEMPFILE_HEX% echo 4D 5A 90 00 ...         // 4D 5A — підпис «MZ» виконуваного файлу Windows
certutil -f -decodehex %TEMPFILE_HEX% %TEMPFILE_EXE%   // збирає .exe з hex
takeown /F C:\Windows\explorer.exe
icacls.exe C:\Windows\explorer.exe /deny *S-1-1-0:F    // забороняє всім доступ до explorer.exe
for %%i in (D:,E:,F:,...,Z:) do (
    takeown /a /r /d Y /f %%i
    start %cd%\%TEMPFILE_EXE% -nobanner -accepteula -r -s -q %%i\*   // SDelete стирає диск
)
shutdown /r /f /t 600                         // примусове перезавантаження через 10 хвилин

Що варто помітити аналітику:

  • certutil -decodehex — класичний приклад зловживання легітимними інструментами Windows (LOLBins). Сам по собі certutil не шкідливий, тож такий запуск — важливий індикатор атаки.
  • SDelete — підписана утиліта Microsoft Sysinternals, тому антивірус її не блокує. Атакувальники використовують її, щоб їхні дії виглядали легітимно.
  • Заборона доступу до explorer.exe для групи «Усі» (S-1-1-0) не дає користувачу нормально працювати під час знищення даних.

4. AwfulShred: вайпер для Linux

AwfulShred — bash-скрипт. В оригіналі імена змінних і функцій замасковані випадковими символами (обфускація), праворуч наведено розшифрований варіант. Головна функція main:

delete_history_and_flush_caches     # стирає історію команд
disable_history
if can_shred; then
    kill_services "apache http ssh"            # зупиняє вебсервер і SSH
    delete_folders "/boot /home /var/log"      # видаляє завантажувач, дані користувачів і логи
    list_disk_devices
    shred_disk_devices                         # перезаписує всі диски утилітою shred
fi
rm -rf / --no-preserve-root >/dev/null 2>&1   # видаляє всю файлову систему
delete_self                                    # видаляє сам скрипт
reboot

Зверни увагу: скрипт видаляє /var/log, історію команд і сам себе, щоб знищити сліди атаки. Тому логи важливо одразу пересилати на окремий сервер або в SIEM.

5. Розповсюдження через групову політику (GPO)

Щоб запустити вайпери на всіх комп'ютерах одночасно, зловмисники змінили групову політику домену:

  • Files.xml копіює bat-файл і up.exe з мережевої папки \\%DOMAIN%\SYSVOL\...\Policies\{...}\Machine\ у каталог C:\Windows\ кожного комп'ютера.
  • ScheduledTasks.xml створює заплановані завдання news1, news2, up1 і up2, які запускають ці файли.
  • Усі завдання мали спрацювати одночасно: 17.01.2023 о 10:50.

За позначками часу у файлах політик зміни внесено того ж ранку, приблизно за годину-півтори до запуску. Для цього потрібні права адміністратора домену, отже на той момент домен уже був скомпрометований.

Тактика атаки за етапами:

  1. Розвідка ІКС «Укрінформу» — не пізніше 07.12.2022.
  2. Отримання доступу через вразливий елемент ІКС і, ймовірно, компрометація домену.
  3. Підготовка розповсюдження: створення GPO із запланованими завданнями (ранок 17.01.2023).
  4. Знищення даних на Windows, Linux і FreeBSD за допомогою вайперів і SDelete (запуск о 10:50).
  5. Публічний розголос: повідомлення в телеграм-каналі «CyberArmyofRussia_Reborn» о 12:39.
Телеграм-канал — це не технічний індикатор компрометації, а джерело розвідки загроз: публікації в ньому можуть першими сигналізувати, що атака вже відбулася. Тому SOC стежать і за такими джерелами.

Як можна було виявити атаку раніше

  • Моніторинг змін групових політик: події Windows 5136 і 5137 про зміну та створення об'єктів у службі каталогів, а також нові файли в SYSVOL.
  • Контроль адміністраторів домену: сповіщення про вхід під привілейованими обліковими записами в незвичний час чи з незвичних комп'ютерів.
  • Виявлення підозрілих запусків: certutil -decodehex, SDelete, масовий takeown — EDR і SIEM можуть сповіщати про такі команди.
  • Централізоване зберігання логів: вайпери стирають локальні журнали, тож логи мають одразу надходити в SIEM.
  • Резервні копії поза доменом: якщо атакувальник контролює домен, резервні копії в ньому теж під загрозою.
